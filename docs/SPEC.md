# Контракты системы (SPEC)

Контракты, на которые опирается остальной код. Контракт меняется осознанно, с
правкой этого файла.

## Идентификаторы (§4)

- **VIN** — ровно 17 символов, латиница и цифры, без `I`, `O`, `Q`.
  Нормализация до проверки: срез крайних пробелов, верхний регистр.
  Регэксп: `^[A-HJ-NPR-Z0-9]{17}$`. См. `fleet/validators.py`.
- **ИНН** — строка из 10 **или** 12 цифр. Хранится строкой, не числом (ведущие
  нули значимы). Регэксп: `^(\d{10}|\d{12})$`.

## Вход водителя (§4)

Контракт `fleet.access.resolve_active_assignment(inn, vin) -> Assignment | None`:
возвращает назначение тогда и только тогда, когда существует **действующее**
(`ended_at IS NULL`) назначение именно этой пары, и ТС не в архиве. Проверять
пару, а не отдельное существование ИНН и VIN. Значения на входе — уже
нормализованные.

Сессия: в cookie хранится только `assignment_id` и время входа; ИНН/VIN в URL не
передаются. Срок — 24 часа. На каждом запросе назначение перепроверяется: закрытие
назначения немедленно лишает старую сессию доступа.

## Расчёт ТО (§6)

Контракт `fleet.maintenance.maintenance_state(confirmed_maint_mileage,
current_mileage, interval_km, warning_km) -> MaintState`:

```
следующее_ТО = confirmed_maint_mileage + interval_km
остаток       = следующее_ТО − current_mileage
```

| Условие                         | status   | color  | текст                         |
|---------------------------------|----------|--------|-------------------------------|
| нет базы (`confirmed = None`)   | NO_DATA  | gray   | Нет данных о последнем ТО     |
| база есть, нет пробега          | NO_DATA  | gray   | Нет данных о текущем пробеге   |
| остаток > warning               | OK       | green  | До ТО осталось … км           |
| 1 ≤ остаток ≤ warning           | SOON     | yellow | Скоро ТО. Осталось … км       |
| остаток = 0                     | DUE      | red    | ТО требуется сейчас           |
| остаток < 0                     | OVERDUE  | red    | ТО просрочено на … км         |

База расчёта — пробег последнего **подтверждённого** ТО, не нуль, не дата отчёта,
не первое случайное показание. Дашборд: «просрочено» = остаток < 0; «требуется» =
остаток = 0; «нет базы» — отдельно, в просрочку не относить.

## Роли и видимость (§4, §7)

- **Администратор** — `is_superuser` или группа «Администраторы»: весь парк.
- **Менеджер** — группа «Менеджеры»: только ТС с действующим закреплением за ним
  через действующее назначение аренды (`vehicles_for_staff`). Рабочая очередь —
  к текущему закреплению; историческая принадлежность отчёта — к
  `Report.manager_at_report` на дату события.
- Проверка прав — на сервере, для каждой страницы, операции и скачивания.

## Ограничения целостности

- Не более одного действующего назначения аренды на ТС
  (`unique_active_assignment_per_vehicle`).
- Не более одного действующего закрепления менеджера на назначение
  (`unique_active_manager_per_assignment`).
- `Report.idempotency_key` уникален — защита от повторной отправки (§5).
- ID ТС (`Vehicle.pk`) неизменяем — основа для будущих платежей/штрафов;
  новые функции не привязывать к тексту VIN (§10).

## Отправка отчёта (§5, §6)

Контракт `fleet.submit`:

- `completeness_errors(report) -> list[str]` — пусто, когда отчёт готов:
  введено показание, есть фото одометра и все четыре ракурса, выбран пункт о ТО;
  при «ТО выполнено» — дата (≤ сегодня) и пробег (≤ показания); при «есть
  замечания» — непустой комментарий. **Просрочка ТО отправку не блокирует.**
- `submit_report(report) -> Report` — атомарно и идемпотентно. Черновик (одна
  строка `state=draft`, один на назначение) переводится в `submitted`: тот же
  `id`/номер. Повторный вызов на уже отправленном возвращает его без изменений.
  Создаёт показание водителя (статус по §6 через `readings.classify_reading`) и,
  при «ТО выполнено», запись `Maintenance` со статусом «на проверке» — никогда не
  подтверждает автоматически. Номер отчёта: `R-<id:06d>`.

## Классификация показаний (§6)

`fleet.readings.classify_reading(...) -> ReadingVerdict(accepted, reason)` —
чистая. На проверку (`accepted=False`), если: конфликт с другим источником за ту
же дату > `GPS_DRIVER_CONFLICT_KM`; значение меньше ранее принятого при не более
поздней дате; прирост относительно ближайшей ранней принятой записи превышает
`ODOMETER_DAILY_JUMP_KM` × число суток. Иначе принято. Отчёт и фото сохраняются в
любом случае; актуальный пробег при статусе «на проверке» не заменяется.

## Вложения (§5, §9)

`fleet.attachments.attach(report, kind, view, uploaded)`. Одиночные слоты
(панель приборов; каждый из четырёх ракурсов) — новый файл заменяет прежний.
Множественные: дефекты ≤5, заказ-наряды ≤5, страницы сервисной книжки ≤5. Фото
проходят `images.process_photo` (JPEG, поворот по EXIF, сброс метаданных,
миниатюра ≤320px, цель ≤2 МБ); документы ТО — PDF или фото, ≤15 МБ.

## Кабинет сотрудников: срез и показатели (§7)

**Срез на дату** `fleet.asof`:
- `accepted_reading_asof(readings, cut)` — выбранное принятое показание
  `(value, date, source)` с наибольшей датой `<= cut` (при равных датах — большее
  значение); `None`, если принятых нет.
- `confirmed_maint_asof(maints, cut)` — база ТО `(mileage, performed_on)`
  последнего подтверждённого ТО с `performed_on <= cut`; `None`, если базы нет.
- Ключ среза ТО — дата **выполнения**, не подтверждения: подтверждение приходит
  позже, но удостоверяет работу до среза. Завершённый месяц считается на последний
  день месяца; текущий — на сегодня. Историческую карточку по сегодняшнему пробегу
  не пересчитывать.

**Сравнение месяцев** `fleet.metrics`:
- `completion_share(submitted, fleet_total)` — доля выполнения, % своего месяца;
  `None` при нулевом парке.
- `compare_months(cur_sub, cur_total, prior_sub, prior_total, complete)` —
  `diff_submitted = cur_sub − prior_sub`; `pct_change = None`, если
  `prior_sub == 0`; `note = "Месяц не завершён"` для неполного текущего месяца.

**Отчётный парк месяца** `fleet.dashboard.reporting_fleet` — уникальные VIN в
области видимости сотрудника, у которых назначение аренды пересекает месяц хотя бы
один день (оба условия пересечения — в одном `filter()` на одну строку связи).
Разрез по менеджеру (только для администратора) — по текущему закреплению.

**Проверка показаний и ТО** `fleet.review` — решение сотрудника имеет приоритет;
исправление требует причины и сохраняет исходное значение в `AuditLog`; отклонение
ТО прежнюю подтверждённую базу не меняет. Все действия журналируются (без секретов
и содержимого файлов).

**Экспорт** `fleet.exports` — `control_table_xlsx(rows, month)` строит .xlsx из уже
собранных строк дашборда (те же значения и срез, что на экране);
`report_zip(report)` — вложения отчёта из закрытого хранилища + `manifest.txt`,
пропавший на диске файл пропускается с отметкой, архив не рушится.

## GPS-импорт из Excel (§8)

**Разбор (чистый)** `fleet.gpsimport`:
- `normalize_mileage(raw) -> CellValue` — целое км; пробелы (в т.ч. неразрывные) и
  десятичная запятая допустимы, дробное вниз с пометкой; формула «=…», пустое,
  нечисловое, отрицательное → `error`.
- `normalize_date(raw, fallback, today) -> CellValue` — `date`; datetime/date и
  строки `ГГГГ-ММ-ДД`/`ДД.ММ.ГГГГ`; пустая допустима при заданной общей дате
  `fallback`; будущая → `error`.
- `classify_import_row(...) -> (RowCategory, reason)` — порядок: `ERROR` (неизвестный
  VIN / негодная ячейка) → `DUPLICATE` (полный дубль VIN+дата+пробег+источник) →
  `REVIEW` (разные показания VIN за одну дату, либо «назад»/«скачок» через
  `readings.classify_reading`) → `READY`.

**Сервис (IO)** `fleet.gpsservice`:
- `build_preview(rel_path, mapping, common_date, today) -> ImportResult` — читает
  .xlsx (`data_only=False`, формулы не вычисляются), первый лист, заголовки в первой
  строке, ≤10 000 строк; сопоставляет колонки по названиям; ничего не пишет.
- `apply_import(...) -> (ImportBatch, ImportResult)` — атомарно: `READY` →
  принятые, `REVIEW` → на проверке, дубли и ошибки пропускаются; партия хранит
  исходный файл, автора, дату и итог (`summary`); при ошибке откат целиком.
- `revert_batch(batch, staff, reason)` — статус `reverted`; записи остаются в
  истории, но из расчёта исключаются (`Vehicle.accepted_reading_rows`).
- `build_template()`, `errors_xlsx(errors)` — шаблон и Excel ошибок (№ исходной
  строки + причина).

Импорт НЕ создаёт фото, НЕ подтверждает ТО, НЕ отмечает месячный отчёт; показания
водителя и GPS не перезаписывают друг друга. Повторная загрузка того же файла
дублей не создаёт. Загружает только администратор (§1).

**`Vehicle.accepted_reading_rows()`** — единый источник «принятых в расчёте»
показаний: `verification=accepted` минус показания из отменённых партий. Используют
дашборд (§7), кабинет водителя и классификация при отправке.

## Массовое подключение парка из Excel (§7)

**Разбор (чистый)** `fleet.onboarding`:
- `normalize_optional_pair(mileage_raw, date_raw, today, label) -> PairResult` —
  необязательная пара «значение + дата»: обе ячейки пустые → пары нет (валидно,
  `error=""`); заполнена одна → `error`; заполнены обе → проверяются правилами §8
  через `gpsimport.normalize_mileage`/`normalize_date` (переиспользованы, не
  продублированы).
- `cross_check_maint_vs_reading(mileage, maint_mileage) -> str` — пробег ТО не
  может быть больше указанного пробега (как в `submit.completeness_errors`).
- `classify_onboarding_row(...) -> (RowCategory, reason)` — порядок: формат VIN/
  ИНН → менеджер известен → пары значений → VIN не повторяется в файле → состояние
  ТС в БД (`READY`/`EXISTS`/`CONFLICT`).

**Сервис (IO)** `fleet.onboardingservice`:
- Колонки (ТЗ §7): VIN, ИНН, Менеджер — обязательны; Госномер, Модель, Пробег,
  Дата показания, Дата ТО, Пробег ТО — по желанию. Лимиты те же, что у GPS (§8):
  ≤10 000 строк, ≤10 МБ, первый лист, формулы не выполняются.
- `build_preview(rel_path, mapping, today) -> ImportResult` — ничего не пишет.
  Менеджер должен существовать как пользователь группы «Менеджеры»; ТС с
  действующим назначением на ТОГО ЖЕ арендатора → `EXISTS` (пропуск); на ДРУГОГО →
  `CONFLICT` (не трогается, бульк-импорт не разрывает действующее назначение).
- `apply_import(...) -> (ImportBatch, ImportResult)` — только `READY`-строки
  создают: ТС (если нет), арендатора (`get_or_create` по ИНН), `Assignment`,
  `ManagerAssignment`, и, если указаны, начальное показание
  (`OdometerReading.source=manual`, сразу `accepted`, без прогона через
  `readings.classify_reading` — это стартовая база нового ТС, конфликтовать не с
  чем) и начальное ТО (`Maintenance.status=confirmed`, `basis=initial`, как в
  `seed_demo`). Партия — `ImportBatch.kind=fleet`.
- Откат для `kind=fleet` **осознанно не реализован**: `gpsservice.revert_batch`
  отказывает с понятным сообщением, не падая. Причина: откат GPS-партии —
  переключение видимости существующих показаний; откат подключения парка означал
  бы разворачивать созданные ТС/назначения/менеджеров — другого рода операция,
  вне контракта, который описывает ТЗ §8 для GPS. Исправление — вручную через
  карточку ТС (закрыть назначение, архивировать ТС).
- `build_template()` — шаблон с девятью колонками и строкой-примером.
  `errors_xlsx` общий с GPS-импортом (`gpsservice.errors_xlsx`), с колонкой
  «Поле», называющей проблемную колонку строки.

`ImportBatch.kind` (`gps`/`fleet`) различает партии обоих импортов на одной
модели; старые записи и демо-данные по умолчанию `gps` (миграция
`0003_importbatch_kind`).

## Файловое хранилище (§9)

В БД — только метаданные `Attachment` (путь, тип, размер, ракурс). Файлы — в
закрытом каталоге `PRIVATE_MEDIA_ROOT` вне веб-корня. Публичных постоянных ссылок
нет: раздача только после проверки роли и доступа к VIN. Имена файлов генерирует
сервер. Структура: `vehicles/<ID_VIN>/reports/<YYYY-MM>/report_<id>/...`.

## Резервное копирование и восстановление (§10)

**Копирование** `scripts/backup.sh`:
1. `manage.py backup_manifest --out manifest.json` — счётчики девяти таблиц
   (`Vehicle`, `Tenant`, `Assignment`, `ManagerAssignment`, `Report`,
   `OdometerReading`, `Maintenance`, `Attachment`, `ImportBatch`) живым запросом,
   снимаются ПЕРВЫМ шагом — верхняя граница для сверки после восстановления.
2. БД: `sqlite3 db.sqlite3 ".backup '…'"` (sqlite) — безопасная онлайн-копия, не
   `cp` файла; `pg_dump -Fc` (postgres, `DB_*` из `.env`).
3. Вложения: `PRIVATE_MEDIA_ROOT` архивируется в `private_media.tar.gz` с
   фиксированным именем верхнего каталога (через временный симлинк) — восстановление
   не зависит от реального пути на исходном сервере.
4. Запись атомарна: шаги 1–3 пишутся во временный каталог, в итоговое имя
   (`BACKUP_ROOT/<YYYY-MM-DD_HHMMSS>/`) переименовывается только по завершении
   без ошибки.
5. Ротация: хранится `BACKUP_KEEP_DAYS` (по умолчанию 30) последних копий по
   сортировке имени (имя — метка времени, хронология совпадает лексикографически).

`BACKUP_ROOT` — отдельное закрытое хранилище вне репозитория и вне
`PRIVATE_MEDIA_ROOT` (по умолчанию — каталог рядом с проектом, не внутри него).

**Восстановление** `scripts/restore.sh [STAMP]`:
- Пишет только в `RESTORE_DIR` (по умолчанию `./restore_test`, в `.gitignore`) —
  рабочие `db.sqlite3`/`private_media` этого дерева не трогает. Без аргумента
  берёт самую свежую копию по сортировке имени.
- sqlite: копия базы + распаковка вложений, затем `manage.py verify_restore`.
- postgres: дамп найден, но автоматическое восстановление в тестовую БД на
  локальном стенде не настроено (нет согласованного сервера) — скрипт печатает
  это явно и завершается, не притворяясь, что проверил.

**Проверка** `manage.py verify_restore --db --media --manifest`:
- Источник истины — манифест, снятый ДО копирования, не сам дамп (иначе проверка
  соглашалась бы с любой его ошибкой). Открывает восстановленную sqlite напрямую
  через `sqlite3`, в обход `DATABASES['default']` — чтобы не свериться с рабочей
  базой процесса вместо реально восстановленного файла.
- Две независимые проверки: (1) счётчик строк каждой из девяти таблиц == манифест;
  (2) для каждого `Attachment.stored_path` — файл существует под восстановленным
  `PRIVATE_MEDIA_ROOT`. Расхождение в любой из двух — `CommandError`, код выхода 1,
  обе строки разбора в выводе (`MISMATCH <ключ>`/`MISMATCH файлы вложений`).
  Обе слепые зоны (запись в БД без файла; файл есть, но БД не совпадает) ловятся
  порознь, одна не маскирует другую.

Проверено разрывом (ТЗ: «прежде чем считать проверку рабочей — сломай то, что она
обязана поймать»): удаление строки `Attachment` в восстановленной копии и
отдельно удаление файла вложения на диске — каждое даёт `MISMATCH` и код выхода 1;
чистое восстановление — `OK` по всем девяти таблицам и файлам, код выхода 0.
